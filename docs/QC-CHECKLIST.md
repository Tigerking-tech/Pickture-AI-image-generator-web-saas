# 交付前检查清单（Visual QC Checklist）

> 这份清单是为了一个具体事故写的：2026-10 交付的展示图把耳机盒底缘啃掉一块，
> 而卡片上还写着 **"6/6 PASS · product fidelity 1.000"**。
>
> 根因不是"没跑测试"，而是**所有检查都没看图**。当时的指标是 MAE / MS-SSIM，
> 它们对「局部啃边」几乎不敏感——缺口只占不到 1% 像素，把背景填得更白反而
> 让 MAE 变好。于是坏的图和"PASS"同时成立。
>
> 所以这份清单的原则是：**每条检查都必须能独立地判定"这张图是不是看着对"**，
> 而且不能复用被测代码的中间结果（自己检查自己必然自证清白）。

## 一条命令跑完

```bash
npm run qc           # 视觉质检：逐张打开展示图，输出清单，失败退出码 1
npm run showcase     # 重新生成展示图，末尾自动跑 qc + edge-audit，不过就中断
npm run edge:audit   # 单独产出边缘放大审阅图（交付前肉眼过一遍）
npm test             # 单元/集成测试
npm run check        # biome + tsc + vitest + qc
```

`npm run qc` 的输出长这样（真实数据，不是示意）：

```
✅ PASS  phones  (bg)
   ✓ 主体轮廓完整（未被啃边，核心区）      1.0000   阈值 ≥0.99；被吃掉 0 像素
   ✓ 背景纯色                     mean 255.0 / sd 0.11   阈值 mean ≥250, sd ≤3
   ✓ 地面带只含中性灰影（无彩色残留）      chroma 0.0 / 覆盖 0%   阈值 chroma ≤6, 覆盖 ≤60%
   ✓ 边缘为羽化过渡（非剪刀边）            0.377   阈值 ≤0.75（原图 0.00 + 0.10 容差）
   ✓ 轮廓贴合真实边缘（未浮空）             1.14   阈值 ≥0.5
   · 主体未顶到画布边缘                 margin 0px   原图本身贴边，仅提示
```

两条判据的由来（都是被真实翻车推着改的）：

- **背景纯色为什么排除地面带**：一旦作用 contactShadow，主体正下方必然有 20–60px 的
  灰度渐变。旧版把它算进"背景"，于是"有影"= "背景不纯"，判据和功能互相打架。
  现在改成：上方+左右仍严格查纯白，地面带单独查"是不是中性灰、有没有铺满"。
- **边缘羽化为什么是相对判据**：这条问的是「去背有没有把软边做成剪刀边」，
  不是「边缘够不够软」。真实照片（深色产品 + 白底）边缘本来就锐，
  处理后依然锐是保真。原图硬切占比 ≥ 0.35 时，这条降级为提示。

## 端到端门禁（线上也拦一道）

`npm run qc` 只查静态展示图。页面是否在浏览器里真的能跑、滑块能不能拖出差异、
控制台有没有报错，要由真浏览器拦一道：

```bash
DEMO_MODE=true npm run start &     # 先起服务（监听 3000）
npm run browser:check              # Playwright 真打开首页 + /demo，逐项出报告
```

`scripts/browser-deep.mjs` 会：① 确认 5 张展示图全部加载成功（防 404/破损）；
② 真实指针拖动对比滑块到两端，读 `--pos` CSS 变量 + 裁剪区域像素 diff 验证
"拖动确实改变了露出内容"（MAE 需 >0.01）；③ 在 `/demo` 逐个点动作真实出图；
④ 收集控制台/页面错误。全部 0 错误才算过。

> 本项目的做法：**把 QC 做成"门禁"而非"报告"**——`npm run showcase` 末尾自动跑
> `qc`，不过就中断；`npm run check` 把 biome + tsc + 单测 + qc 串成一条命令。
> 任何一步红，提交/发布前就会卡住，坏的图根本出不了门。

坏图跑出来是这样，一眼就能看出问题：

```
❌ FAIL  phones  (bg)
   ✗ 主体轮廓完整（未被啃边）           0.9734   被吃掉 8844 像素
   ✗ 边缘为羽化过渡（非剪刀边）            1.000   硬切 3181/3181 边界点
```

## 检查项与阈值

| # | 检查项 | 指标 | 阈值 | 抓的是哪类事故 |
|---|---|---|---|---|
| 1 | 主体轮廓完整 | subject recall（RMBG 参考蒙版**腐蚀 2px 后**的核心区 ∩ 输出前景；原图本身接近底色的像素不计入分母） | ≥ 0.99 | **啃边 / 削角 / 主体被裁** |
| 2 | 背景纯色 | 背景区亮度均值 / 标准差（**画布下方 30% 的"地面带"不计入**，那里本来就该有影） | ≥ 250 / ≤ 3.0 | 背景残留、脏底、渐变 |
| 2b | 地面带干净 | 地面带背景像素的平均通道差 / 被压暗像素占比 | chroma ≤ 6 / cover ≤ 60% | **彩色残留、整条灰带糊底** |
| 3 | 边缘羽化 | 硬切边界点占比（背景像素紧邻强前景且无过渡像素）；**仅当原图本身是软边（< 0.35）时才是硬门槛** | ≤ 0.75 | **剪刀边、锯齿、二值抠图** |
| 4 | 轮廓贴合 | 蒙版边界带（alpha 0.45–0.55）原图梯度中值 ÷ 全图 p99 | ≥ 0.5 | **轮廓浮空 / 与真实边缘错开** |
| 5 | 主体不贴边 | 前景 bbox 到画布最小边距 | > 1px（info） | 构图裁切 |
| 6 | 调色方向 | R−B 均值位移 | > 2 | 暖调做成冷调 |
| 7 | 调色幅度 | MAE | > 6 | "改了但看不出" |
| 8 | 缩放目标 | 输出尺寸 | == 目标画布 | 缩放比例错 / 拉伸 |
| 9 | 水印生效 | 与原图 MAE | > 0.05 | 水印没叠上 |
| 10 | 非空白 | 近黑像素占比 | < 0.5 | 全黑/全白输出 |

阈值集中定义在 `scripts/qc.mjs` 顶部的 `TH`，改动请同步本表。

## 为什么这些指标能抓住「看图才发现」的问题

- **MAE / SSIM 是全局平均**：一个 8 千像素的缺口在 108 万像素里只占 0.8%，
  对平均值影响极小；而"填白更彻底"还会让 MAE 变好。它们测的是"整体像不像"，
  不是"轮廓对不对"。
- **subject recall 测的是几何一致性**：先用语义分割模型在原图上得到"主体应该
  在哪"，再回到输出图上逐个像素问"这里还是主体吗"。啃掉的边会被完整计分，
  而且**不依赖被测引擎自己的蒙版**。
- **边缘硬度测的是过渡带**：正确的软 alpha 合成会在物体与背景之间留下 1–2px
  的混合像素；二值漫水填充没有这一层，边界像素不是纯背景就是纯物体，一测就露。

## 「边缘干不干净」是自动化抓不住的那一类

2026-10 第二次返工的教训：QC 全绿（20/20），但把图放大 5 倍一看，边缘还是
「台阶 + 毛刺」。我试过三种量化指标想把这件事测出来，都在真实数据上失败了：

| 试过的指标 | 结果 |
|---|---|
| 轮廓法向抖动的 RMS（移动平均去趋势） | 原图 0.42px / 修好 0.37px，**区分度不足 1.2×** |
| 过渡带宽度变异系数（10–90% 上升宽度） | 受白底反推 mask 的阈值影响，噪声压过信号 |
| 形态学粗糙度（mask 与开/闭运算的差） | 0.001 vs 0.000，**几乎为 0** |

结论不是"指标写错了"，而是**这类问题的信息量集中在 1–2 个像素里**，一旦从
白底合成图上反推蒙版，量化与阈值化就把差异抹平了。任何基于"重算蒙版"的指标
都会在这里失效。

所以改成分工：

- **自动门禁**负责"灾难"：啃边、脏底、剪刀边、轮廓浮空——这些能可靠测量。
- **人眼负责"干不干净"**：`npm run showcase` 结尾自动产出
  `public/showcase/edge-audit.png`——按轮廓均匀取 12 处、每处 100×100 放大 5 倍
  的宫格图。**交付前必须打开看一眼**，这一步不能省，也不该假装被自动化替代。

### 这次返工的真正根因（两个）

1. **几何失真**：把 w×h 硬拉成 1024×1024 喂模型，1200×900 变成 0.853/1.138
   的各向异性缩放，模型看到的是变形的产品，边界自然是偏的。
   → 改 letterbox（等比+居中填充），推理后裁回原比例。
2. **网格台阶被放大**：1024 的 mask 放到 1200，每级台阶变成 1.17px 的直角。
   双线性放大只能把台阶抹成斜坡，抹不掉台阶。
   → 把 mask 当**几何区域**处理：二值化 → 去小岛/填洞 → EDT 有符号距离场
   → 对距离场做高斯平滑（等值线被拉直）→ 0.9px 窄羽化重建 alpha。
   平滑的是距离场而不是 alpha，所以过渡宽度不会被越抹越糊。

配套还加了一步**边缘去灰**（`bleedColor`）：原图背景色混在半透明边缘里，
直接合成会在白底上留一圈发灰的脏边，所以先把轮廓 1–2px 内的颜色换成内侧
前景色再混合。

## 已知边界（不假装覆盖）

- 语义分割对**透明/反光/细发丝**类目仍有误差，QC 的 subject recall 用的是同一
  模型的判断，两者会一起偏——这类素材需要人工复核。
- 参考掩版来自单模型单尺度，主体占比极小（<2%）时不可靠。
- QC 只检查"几何与底色是否正确"，不判断审美（构图、光影是否好看）。

## 调色类：中性色不得被染色（2026-10 番茄红事故的防线）

去背之后再做暖调，最容易出的事是**把灰底/白盖一起染成橙色**，或者把琥珀推成番茄红。
`tests/lib/grade.test.ts` 固化了 5 条判据：

| 用例 | 判据 | 抓的是 |
|---|---|---|
| 琥珀 #A0522D | 输出仍满足 g−b > 15 | 通道裁剪导致的番茄红 |
| 深蓝 #263E6E | 输出仍满足 b > g > r | 暗部负值导致的荧光绿（OKLab cbrt 对负值有定义） |
| 中灰 #969696 | R−B < 25 | 中性像素被分离色调染色 |
| alpha=0 区域 | 输出像素不变 | 白底被调色污染 |
| 极暗 #020306 | 无 NaN、无越界 | 线性域负值未夹住 |

## 防回归

`tests/lib/rmbg.test.ts` 固化了第一次事故的判据：对 `phones.png` 去背后，
主体保留率必须 ≥ 0.99、硬切边界占比 ≤ 0.75。任何人把去背改回颜色容差，
这个测试会直接失败。

`tests/lib/refine-alpha.test.ts` 固化第二次返工（边缘台阶）的判据，用合成数据
（3px 方块化的圆）逐条锁死：EDT 数值正确、锯齿半径波动至少降 25% 且归到
0.7px 以下、轮廓尺度不被撑大或吃小、alpha 仍是软过渡、孤立小岛被去掉、
内部空洞被填上。删掉 `refineAlpha` 里的任何一步，这里会红。

## 业界视觉 QA 工具调研（2026-10 检索）

核心事故（局部啃边）本质是**像素级视觉回归没做**。调研了主流方案，结论如下：

| 工具 | 类型 | 免费额度 | 适合本项目吗 |
|---|---|---|---|
| **Playwright `toHaveScreenshot`** | 开源/代码内 | 免费（MIT） | ✅ 已用（本项目 `browser-deep.mjs` 即此路线） |
| **BackstopJS** | 开源 CLI | 免费（MIT） | ⚠️ 适合整页 URL 快照，需配 config |
| **Percy (BrowserStack)** | 云 SaaS | 5,000 截图/月 | ⚠️ 跨浏览器强，但需 CI 集成 + 付费 |
| **Chromatic** | 云 SaaS | 5,000 快照/月 | ❌ 绑定 Storybook 组件库，不适用 |
| **Applitools Eyes** | 云 SaaS（Visual AI） | 试用 $667/月起 | ⚠️ AI 降误报强，但贵、要 SDK |
| **jest-image-snapshot** | 开源 | 免费 | ⚠️ 适合 Jest 栈 |

**选型结论**：

1. **像素 diff 只能抓"变了"，抓不了"变坏了"**。这正是本次事故的根因——
   旧指标 MAE/SSIM 是全局平均，啃掉的 0.8% 像素被淹没。所以光上 Percy/Playwright
   的截图比对**不够**，必须在比对之外加"语义级几何判据"（subject recall、
   边缘硬度）——这部分没有现成商业工具能替代，是本项目的 `qc.mjs` 自建的。
2. **Playwright 是性价比最优选**：已免费内置、能真实拖动滑块、能抓控制台错误，
   与现有测试栈一致。重型云方案（Applitools/Percy）的"AI 降误报"价值，在本项目
   体量下不值得引入月度成本；它们也仍然需要你先定义"什么算坏"。
3. **真正的"一次就过"靠的是门禁化**：工具只是手段。把 `qc` + `browser:check`
   串进 `check` 与发布流程，让坏产出在交付前被自动卡死，比任何单点工具都重要。
